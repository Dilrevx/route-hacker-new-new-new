# HCVR 抽样重建与重复缓存清理

2026-10-01，在历史修复记录归档之后，按“Maven 和 Ant 各重建一个样本，其余只检查登记输入”的范围执行。两个样本均在新目录中重新解包源码、编译并生成新的 CodeQL 数据库，没有复用旧数据库或旧构建输出。

## 两个样本实际验证了什么

| 样本 | 重建条件 | 本次结果 |
| --- | --- | --- |
| JStachio，精确 commit `9ce20009…` | JDK 17.0.12+7、Maven 3.9.8、CodeQL 2.23.2；新 HOME、新 Maven 缓存；在线下载依赖 | 首次构建 725.416 秒，退出码 0；数据库 finalized，98 个 Java relation 均非空；无构建重试 |
| Tomcat，精确 commit `7d50e72f…` | JDK 21.0.11、Ant 1.10.14、CodeQL 2.23.2；新 HOME/source/DB；离线、只读挂载已有依赖 | 构建 84.152 秒，退出码 0；数据库 finalized，96 个 Java relation；4,521 个原源码文件与 11 个依赖文件均未改变 |

两次构建均限定 2 个 CPU，设置内存监控和 900 秒构建时限。完整源码 SHA256、commit、验收字段和私有原始回执哈希见 [sample-rebuilds.json](sample-rebuilds.json)。

Tomcat 的历史案例标签写 **11.0.2**，但该归档对应的精确源码在 `build.xml` 中声明 **12.0**。本次没有换源码凑标签：通过的是这个精确 commit 的构建，不是对“11.0.2”版本身份的确认。

这是编译与 CodeQL 建库验证，不是应用启动或 PoC 验证。源码、工具链和依赖仍是必要输入：Maven 本次需要联网；Ant 使用了 ecj 4.34、commons-daemon 1.4.1、migration 1.0.9、bnd 7.1.0 四个已有依赖目录，共 11 个文件。没有据此删除这些材料。

### 修复说明怎样用于重建

1. 按历史来源取得精确 commit 的源码包，核对 SHA256，在新目录解包；不要按项目名或标签换成其他版本。
2. 选择记录中的工具链，使用独立 HOME 和依赖目录。Maven 的目标为 `-DskipTests -DskipITs -Dmaven.test.skip=true package`；Ant 使用 `ant`，并提供上述只读依赖。
3. 通过 `codeql database create --language=java --threads=2 --ram=6144 --source-root=... --command ...` 新建数据库；检查构建退出码、`codeql resolve database --format=json -- ...`、`finalised: true` 和非空 Java relation。

这是命令要点，不是省略输入准备的一键脚本。首次使用了当前 CLI 不支持的 `database info`，Maven 验收器还修正过一次 YAML 判断的假阴性；原失败验收记录均保留，构建本身没有因此重跑或改写为其他结果。

204 个案例在检查位置仍有登记的源码目录及源码包；9 个案例在这些位置两者都缺失，名单见 [input-check-summary.json](input-check-summary.json)。这不表示整台机器没有其他副本，也不表示存在的目录内容完整。没有因为抽样通过，就把 213 个案例全部标为可复现。

## 清理范围与恢复

清理只涉及两轮失败尝试中的 **8 份 Maven 缓存**。逐文件比较公共 seed 后，为相同内容另存独立、按 SHA256 去重的恢复副本；再次检查原文件、恢复副本和当前使用状态后，才逐文件删除。

清单包含 535,248 个相同文件，逻辑大小 74,029,946,792 bytes。3,943 个未纳入删除的文件留在原处，包括 3,927 个 seed 中不存在的文件和 16 个空文件。目录、源码、CodeQL 数据库、日志、公共 seed 和其他独有内容没有删除。实际删除数、分配块占用及扣除恢复包后的空间估算以 [cache-cleanup-summary.json](cache-cleanup-summary.json) 的最终回执为准，而不是用逻辑文件大小冒充磁盘净释放量。

本轮删除文件原占用约 75.64 GB，独立恢复包占用约 10.15 GB；相减估算缓存所在磁盘净释放 **65.49 GB（60.99 GiB）**。这个口径不包含另一磁盘上的新构建目录和审计副本，也不是整台共享服务器的 `df` 差值。[清理后独立复查](post-cleanup-check.json)再次确认全部 535,248 个删除路径不存在、3,943 个保留路径仍存在，8 个案例的登记源码、数据库、公共 seed 和原始回执路径均仍存在。

恢复包包含完整路径映射、66,849 个去重后的字节对象、两份绑定原目录的历史回执和恢复脚本；独立字节副本不是旧缓存的硬链接。完整映射的压缩副本及本次验收材料另存本地私有归档。**GitHub 只有说明、摘要和工具，不含这些依赖字节，因此不能删除保留的恢复包。**

已从真实恢复包中选取 21 bytes、788 bytes 和 760,687,965 bytes 三个文件恢复到新目录，重新核对内容 SHA256、大小、权限和修改时间。恢复工具另通过 30 项 Linux 隔离测试，见 [restore-tests.json](restore-tests.json)。初次真实恢复检查遇到中间目录不可列举的问题；仅改为使用允许的路径遍历方式，未改变服务器权限，原失败记录保留。

将恢复包完整保留或整体迁移后，可运行 [restore_cache.py](restore_cache.py)：

```bash
python3 restore_cache.py \
  --manifest /absolute/path/to/retained-store/cache-retirement-plan.json \
  --destination /absolute/path/to/new-empty-directory
```

输出是 `<候选编号>/<原缓存内相对路径>`，并生成 `restore-receipt.json`；只写新空目录，不自动覆盖旧路径。可以追加 `--indices 5646,282711,468344` 重做上述三个文件的恢复测试。全量计划解析需要预留数 GB 内存，恢复全部重复副本需要约 74 GB 文件空间。

使用状态检查覆盖可读取的进程路径、当前用户可读文件描述符及运行中的 Docker 挂载，不宣称能查看受保护系统进程的全部文件。跨案例引用检查限于已索引的控制材料，不是全服务器依赖证明。恢复包与原有唯一输入都继续保留。
