# HCVR 历史环境修复记录

这里按案例保存 HCVR 实验中修复编译环境和构建 CodeQL 数据库的经验，方便以后找到同一项目、同一版本的修法。原来的 v8、v9、v10 是实验工作区，不是三份互相替代的数据集。本页主体及案例索引是首次归档的历史材料；后续执行的[两例独立重建、输入检查和重复缓存清理](rebuild-check-20261001/README.zh-CN.md)单独记录，不改写历史状态。

本次为 213 个历史案例建立入口。其中 141 个案例有实际修复尝试或明确数据库 readiness 的整理记录；共保留 787 组去重后的记录，包含 99 组建库修复成功、8 组已有数据库就绪和 680 组失败或阻塞记录。62 个案例出现过建库修复成功记录。这些都是所收集历史材料的计数，不是当前成功率，也不是独立尝试次数或漏洞确认数。

另有 72 个案例仅保留私有上下文索引，没有在本次有界收集范围内提取出符合条件的公开修复尝试；不据此断言它们从未修好。完整私有小文件共 7,002 份、256,182,040 bytes，约 256 MB。

## 按项目找到修法

从[可点击的案例目录](CASE_INDEX.zh-CN.md)按项目名、CVE 或完整 `case_id` 查找，也可以使用[结构化索引](case-index.json)。同一案例的多轮修复记录放在一起，不只留最终成功计数。整理版重点保留实际 `repair_attempt` 和明确的已有数据库 readiness 记录；输入队列、提案、未执行计划及其失败原因仍在私有原始材料中，没有删除。

每条记录包含历史状态、修复动作或命令、工具链信息及原始记录定位。信息缺失时保留未知，不根据项目名称推测版本或失败原因。命令是历史材料，不是可以在当前工作目录直接执行的安装步骤。

`duplicate_source_references` 将相同修复对象及相同外层状态在多份汇总中的引用关联起来。仅对后缀与实际 v8 案例目录完全一致的 `v8:`、`v8_` 前缀做归一化，不按 CVE 猜测合并不同项目或版本。

## 怎样理解成功

编译成功、CodeQL 建库成功、查询成功、服务可以启动、漏洞得到动态确认，是不同层次的结果。审计文件中的 `passed` 也可能只表示记录或输入检查通过。本索引保留原始状态字段，并单独注明证据类型；不能把所有通过状态合并成复现成功数。

尤其要看一轮记录是否只有 `database_repaired`，但尚未进入 readiness 发布。失败尝试也有价值：它们记录了无效的工具链组合、缺失依赖和已经试过的命令，下一次修复可以避开这些重复工作。

## 时间线和依赖

| 阶段 | 当时的工作 | 与其他材料的关系 |
| --- | --- | --- |
| v8 初始工作区 | 为 213 个案例获取精确版本源码并尝试建库 | 原始源码、回执和建库工作区被后续阶段引用；目录中存在数据库不等于建库成功 |

| v10 多轮修复 | 在隔离构建目录中反复尝试修复、重新创建数据库，并审计结果 | 每轮记录和方案是主要知识成果；大量磁盘占用来自每次尝试复制的依赖缓存 |
| 后续 compile 和 runtime | 更晚的编译配方、CodeQL 修复与运行环境工作 | 另见[已有修复说明](../REPAIR_GUIDE.zh-CN.md)；有重叠项目，但验证范围与版本必须分别核对 |

具体记录时间和目录日期分开保留。文件修改时间只用于定位历史副本，不证明实验发生时间；没有明确完成时间的记录不人为排列先后。

## 保存了什么

本归档保存可检索的修复知识和来源索引。原始小型控制文件另有本地私有副本，并核对内容哈希；对外整理版去除私人机器路径和敏感字段。原始文件哈希与整理版哈希分开登记，摘录不冒充原文件。

源码、完整 CodeQL 数据库、依赖缓存、镜像、完整构建日志和模型对话没有因为出现在索引里就获得完整备份。首次归档没有删除服务器材料；后续先对 8 份旧缓存中的相同文件另存独立恢复副本后清理，详见[首次执行记录](rebuild-check-20261001/README.zh-CN.md)。10 月 2 日又对另外 14 份缓存按同样的逐文件核验原则清理，复用已有独立恢复副本，估计净释放约 121.80 GB，见[第二批记录](cache-cleanup-20261002/README.md)。唯一源码、数据库、公共依赖和未满足清理条件的缓存文件仍保留；GitHub 摘要不替代独立恢复库。若以后要恢复运行，应先核对配方引用的输入是否仍可取得，再在隔离环境中重建并重新验证。

同日的[第三批清理](cache-cleanup-20261002-catalog/README.md)又处理 35 份缓存、30 个不同案例，删除 1,575,824 个已有独立恢复副本的重复文件，保留 59,307 个未匹配或空文件，估计净释放 268.83 GB。源码、数据库和修复记录未删除；本批未重新构建项目。剩余目录并非一律必须保留，后续仍需按实际备份覆盖和占用检查逐批处理。

见[来源清单](source-provenance.json)、[交付文件清单](file-manifest.json)和[归档完整性验证](verification.json)。完整性验证工具只检查文件、哈希、索引和来源关联；实际构建证据见独立重建记录。两个样本通过不代表 213 个案例均已重新验证。
